# iCloud preservation, restore and device sync design

Date: 2026-10-31. Status: proposed follow-up; documentation only. No implementation, entitlement, account check, cloud transfer or deployment is claimed. GitHub App + MCP product parity remains the first release. This design does not enlarge that release or authorize native signing/account setup.

## Intent and product decisions

Use the Mac user's existing system iCloud account, without Sign in with Apple or another Sticker login. Provide historical preservation and recovery first; add same-account device editing separately. The product chooses safe mechanics. Ordinary use requires **zero custom JSON, filesystem paths, tokens, server addresses, account nicknames or sync-strategy input**. Only a meaningful data target, OS/provider permission, external-data consent and destructive replacement consent may require the user's decision. A technical choice wizard is an acceptance failure.

Account status, backup and record synchronization are different facts. `available` does not mean a backup uploaded, and a successful record send does not prove all devices received it. Do not show an Apple Account email, device serial number, Apple device inventory, total free iCloud quota or continuous background sync that these providers cannot establish.

Engineering approaches considered:

1. Put live SQLite/WAL and uploads in iCloud Drive: rejected; independent replication cannot preserve DB/file transaction boundaries.
2. Immutable archives only: selected for the first user-facing iCloud release; useful, bounded, recoverable. It does not synchronize edits.
3. Immutable archives plus a separate CloudKit record protocol: selected as the staged destination, after synthetic and authorized live validation. It costs explicit durable reconciliation, but supplies device editing without pretending an archive is a merge engine.

These are proposed engineering defaults under the user's instruction to avoid technical choices, not a claim of approval for cloud account changes or real data movement.

## Evidence and current limits

The current source installer creates an ad hoc signed app targeting macOS 11.3. This foundation adds no Apple entitlements, provisioning profile, account access or CloudKit container. A future native adapter must satisfy Apple's supported signing and iCloud capability requirements and verify them separately; a local SDK or successful synthetic test is not evidence of account connectivity. The official API references below define the proposed integration boundaries.

Current paths: `server/domain.ts`, `server/store-context.ts`, `server/migrations/001-initial.ts` through `010-github-app-sync.ts`, `server/features/resources.ts`, `server/features/relations.ts`, `server/backup-validation.ts`, `server/maintenance.ts`, `scripts/backup.sh`, `scripts/restore.sh`, `packaging/macos/{AccessCore,StickerApp}.swift`. Existing backup stops the service; existing restore validates staged data and leaves it stopped. GitHub restore preparation already disables its binding and marks queued/sending jobs uncertain. That is insufficient for the new credential-free archive and account fence.

No new dependencies. Use existing Node 24 built-ins, SQLite, zod, React/test tooling and native Foundation/CloudKit. Keep the shell deployment target at **macOS 11.3**. Gate `CKSyncEngine` paths with **macOS 14.0+**; on older systems expose `SYNC_OS_UNSUPPORTED`, while local work and independently supported archive functionality remain usable. No custom older-macOS change-token adapter is included.

## Account, identity and native boundary

`CloudAccountProvider.status()` uses `CKContainer.accountStatus`; identity resolution uses `userRecordID` only after availability. Observe `CKAccountChanged`. Drive uses the opaque `FileManager.ubiquityIdentityToken` for equality/change detection, and obtains the entitled container URL through `url(forUbiquityContainerIdentifier:)` off the UI thread. Never parse the token, guess a Mobile Documents path, inspect Keychain/accounts, request Contacts/discovery, or use a user-supplied Apple email. These API roles and limits are documented in the feasibility report's **What public APIs can display** section.

Represent CloudKit and Drive independently. CloudKit availability does not prove Drive enabled; either identity-change signal immediately fences both transports until fresh resolution. Runtime provider states: `available`, `no_account`, `restricted`, `temporarily_unavailable`, `could_not_determine`; capability errors separately include `NOT_CONFIGURED`, `BRIDGE_UNAVAILABLE`, `NATIVE_BRIDGE_REQUIRED`, `SYNC_OS_UNSUPPORTED`. Do not convert a missing entitlement into `no_account`.

UI shows `iCloud 계정: 사용 가능` (or precise reason), `이 Mac의 시스템 iCloud 계정을 사용합니다.`, checked-at time, and `앱 계정 식별자` from a shortened SHA-256 digest of container/environment/user record ID. If unavailable, show `확인되지 않음`. No nickname field. Optional explanatory text: `이메일은 이 연결 방식으로 확인할 수 없습니다.` The full ID/token never appears in UI, MCP or routine logs. This identifier is neither an email nor globally stable across apps/containers. Device labels are automatically `이 Mac` locally and `Sticker 기기 <short random installation ID>` elsewhere; they describe Sticker installations only.

Private binding key is `(container, environment, provider identity, dataset UUID, generation UUID)`. Add monotonically increasing local `accountEpoch` and `restoreEpoch`; the device UUID is generated per installation, never imported from backup. Local-only data starts unbound. Each account gets a separate local dataset/cache, not a filter over another account's records. Detection alone never uploads or attaches local data. Initial attach shows the concrete existing cloud workspace or current local workspace with count/size and one primary action. With more than one cloud workspace, a data-target selection is legitimate; no merge/replace/CRDT strategy picker.

On A→B, sign-out or uncertain identity: increment epoch transactionally, stop new claims, cancel native requests where possible, quarantine A's pending jobs, discard stale callbacks and release Drive handles. Clear displayed A identity immediately. A delayed completed network operation may already have affected A; record its outcome as uncertain until readback in A, never reuse it in B. Native preflight must resolve/check identity immediately before each operation; epoch guards cannot retract bytes already accepted by Apple. If the provider changes during an operation, stop publication, retain uncertainty and require authorized account-specific reconciliation. Do not claim an impossible cross-account atomicity guarantee from status checks alone. Gate real publication on native integration evidence for account-transition behavior; if it cannot establish a trustworthy identity at dispatch, return `ACCOUNT_UNCERTAIN` and retain local bytes.

Native process operates while the app is running, independently of WebView visibility. Use a narrow native client of an authenticated loopback job API, not a generic WKWebView shell bridge or a public listener. Local Docker only; no host home-directory mount. Launcher establishes a one-run bridge capability through private pipes/0600 application staging, never user input or model-visible output. Server verifies exact allowed job kinds, process-instance nonce, bounded payloads, claim epoch and owner-approved scope. Revoke on bridge exit/service restart. Same-machine hostile-root resistance is not claimed. No Apple credentials enter Docker.

Bridge lease: 30 seconds, renewable every 10 seconds; one archive job and one record exchange maximum, serialized against maintenance. Every claim/ack carries job ID, attempt UUID, epochs, dataset/generation, payload digest. An expired lease after dispatch is `uncertain`, requiring receipt/manifest readback before resend. Lease expiry alone is not failure proof. Native durable journal in its app-support area supports archive work while the server is stopped; server job row alone cannot orchestrate its own shutdown.

## Common UI and MCP product jobs

One `CloudService` owns permission, idempotency, validation, progress and state; HTTP and MCP are thin clients. Reuse the owner MCP path from the preceding parity release; a scoped agent does not silently become owner. Account identity, workspace backups, restore and account attachment require owner. Project agents may read only project-scoped sync status/conflict counts, never other-project bytes/account identifiers; conflict editing remains subject to the domain's owner/closed-issue rules.

Operations: `account.refresh`, `backup.create/list`, `restore.preview/apply`, `binding.preview/attach`, `sync.pause/run/status`, `conflict.list/save`, `device.list`, `job.get/cancel`. Give discoverable MCP names `sticker_icloud_<operation>` with dots represented by underscores. Status/list/preview are reads; apply/attach/cloud publication use explicit idempotent product jobs. MCP can perform all app-owned steps without opening a browser. An OS sign-in/permission step is reported `SYSTEM_ACTION_REQUIRED`; no agent prompts for the Apple password.

`submit(actor, request, operationId)` returns `{jobId,state,progress,errorCode}`. Strict request unions contain opaque target/preview IDs and domain content, no generic filesystem/URL/command/strategy fields. Key `(actor identity, operation kind, operationId)` plus payload hash; same replay returns same job, different payload rejects `OPERATION_CONFLICT`. States: `queued`, `running`, `waiting_system`, `waiting_network`, `local_complete`, `upload_pending`, `uploaded_os_reported`, `completed`, `conflict`, `failed`, `canceled`, `uncertain`. Job-kind-specific validators prevent nonsensical transitions. Cancel after publication acknowledges that bytes may already exist; never labels it rollback.

Separate status timestamps/counts: account checked, locally verified snapshot, OS-reported upload, cloud fetch, cloud send, pending records/assets and unresolved conflicts. `synced` is permitted only as `up to date as of <time>` after fetch+send complete with no pending/conflict under the same binding; it never means all Macs received it. Report measured app-local bytes, not a fabricated iCloud quota meter.

## Immutable credential-free preservation

The existing whole-volume tar is not the new cloud format. Produce a fresh SQLite export from explicit table/column allowlists; deleting secret rows from a copy can leave them in freelist pages, WAL or journals. Do not use that as sanitization. Reject unclassified schema/table/column additions until the export policy and fixture are updated.

Archive `formatVersion=1`: manifest, fresh `sticker.sqlite`, and committed referenced `uploads/<storageUUID>` bytes only. Manifest contains snapshot UUID, source dataset/generation, app/schema/export-policy versions, capture time, file SHA-256/size inventory and totals. It contains no raw provider identity or installation credential. Content may itself include private prose/documents; explain that content is sent, and do not silently remove user attachments by secret-looking heuristics.

Export policy for current schema:

| projects, versions, issues, comments, activity, attachments                                                                         | Explicit content columns; preserve IDs and local history                                               | Sync content, UUID identity; revision translation below                |
| issue relations, resources, all resource versions, issue-resource links, resource events                                            | Include content and referenced bytes                                                                   | Include with version identity and graph rules below                    |
| templates/template versions and issue template provenance                                                                           | Include content                                                                                        | Include with immutable-version mapping                                 |
| release changelog/history/audit and issue change/field history                                                                      | Include historical content; audit is evidence, never authority                                         | Immutable history events; translate local revision slots               |
| agent_reports, agent_sessions, session_events/requests/responses, session_resource_refs                                             | Empty in the fresh DB; explicitly excluded, including historical session records for this first format | Not synchronized; no current liveness or workflow-session resurrection |

Before sealing, convert each unresolved content conflict into deterministic ordinary recovery resources in the fresh export DB (resource UUID derived from snapshot UUID + conflict UUID, version 1, title `보관된 별도 변경`, markdown containing escaped B/L/R content and source UUIDs). Copy any referenced alternative asset bytes through the same inventory; no executable jobs, tokens, CloudKit system fields or lease data enter that projection. The restored resources are inert content, never active conflict resolutions. Preserve later `cloud_history_events` through explicit content-column allowlisting. Preserve the schema's required empty tables so existing validation remains applicable. Do not call this a complete environment clone: UI preview plainly lists excluded sessions, preferences and external connections. A pre-restore safety snapshot uses this same content format; existing private credentials are not replaced, and all active authority is separately invalidated/fenced. No session or live outbound job is included merely for convenience.

Snapshot protocol:

1. Acquire one cross-process maintenance lock. Refuse if another backup/restore owns it. Drain HTTP/MCP operations, multipart callbacks, file commits and sync; stop the service and close SQLite. A 30-second drain timeout fails before snapshot. Remember prior running state.
2. Under that closed boundary, native supervisor invokes a fixed packaged export/validation command against the named app volume; no arbitrary command from clients. Create fresh staging DB using shipped schema; copy explicit content values in a transaction; copy exactly referenced committed files while the service remains stopped. No symlink/hardlink/device members. Use restrictive staging and clean failed exports.
3. Validate SQLite integrity/FKs plus domain invariants, current manifest, checksums and reference inventory. No WAL/SHM, session or secret sidecar. Seal/fync files and manifest, atomic rename within local staging. Resume service if previously running, even when later transport fails. Snapshot remains immutable.
4. Publish a unique `.stickerbackup` directory package to the entitled Drive container with coordinated file access, temp sibling then finalized name; peers only list a finalized package with valid completion manifest and downloaded inventory. Manifest/hash verification is mandatory even after rename, since cloud propagation is not a transactional folder copy. Recover listing from manifests, not a mutable latest pointer.
5. Observe ubiquitous upload/download keys and metadata events. Show `uploaded_os_reported` only when every archive member is OS-reported uploaded. Partial/placeholder packages are not ready; trigger native download, await completion then verify before preview. Retain local verified archive on quota/network errors. No automatic retention deletion in v1.

Initial engineering bounds: at most 1 GiB total exported uncompressed content, 50,000 files, 1 MiB manifest; preserve existing individual file limits (currently 20 MiB). Preflight available staging space for two archive copies plus a 64 MiB reserve; unknown capacity refuses safely. These are fixed product limits, surfaced as `BACKUP_TOO_LARGE`/`INSUFFICIENT_LOCAL_SPACE`, not user-tunable settings. Larger datasets remain local and require a future implementation, not an incomplete archive labeled complete.

## Restore fences and crash consistency

Preview downloads and fully validates; binds snapshot digest, supported schema/export policy, current dataset/generation, account/restore epochs, current dataset mutation sequence, excluded-data disclosure and exact replacement scope. Apply requires owner confirmation of this preview. Any intervening local mutation or account change returns `RESTORE_PREVIEW_STALE`; regenerate the preview rather than widening approval.

Apply first acquires the exclusive cross-process restore lock and closes mutation admission for HTTP, MCP, multipart/file finalization, sync import and background domain writers. Drain every already-admitted mutation; only then revalidate the exact preview snapshot digest, dataset mutation sequence, active-root ID, binding/dataset/generation and both epochs. The sequence covers every accepted content mutation and file-reference commit. A mismatch returns `RESTORE_PREVIEW_STALE`, leaves the old root and its newly accepted writes intact, and requires a fresh preview; never widen the earlier approval. A drain timeout likewise never proceeds to replacement.

Keep that same uninterrupted admission fence from the final check through stop/SQLite close, old-root safety snapshot capture and verification, restored-root staging, journal publication, pointer switch and startup validation. Use `captureContentSnapshot` in an internal already-fenced/no-resume mode: its ordinary backup restart behavior must not run inside restore. No helper may reopen admission or resume cloud publication. Revalidate binding, both epochs and active-root ID immediately before pointer publication under the same coordinator lock; an identity-change event invalidates the fence even while service writes are blocked.

Stage complete restored DB/uploads in a new data root. Do not rename DB and uploads independently: write a durable restore journal with old/new root IDs and the validated consent boundary, fsync it and atomically switch one active-root pointer on the same filesystem. A startup recovery command must finish/read this journal before app service admits writes. Before pointer switch the old root is authoritative; after switch the new root is authoritative. Keep the old root until explicit recovery retention later; no automatic deletion in v1. Volume-root indirection and boot recovery are prerequisites, not capabilities of today's scripts.

Restored content gets a fresh dataset generation, incremented restore epoch and fresh device UUID. Outboxes, sync tokens/system fields, native leases, cookies/auth sessions and all GitHub bindings/jobs are empty/disabled; regenerate installation-bound state. Keep current external credential storage separate and do not auto-enable it. Initial service restart opens the restored local workspace with cloud publication paused. The local restore never overwrites other devices. A subsequent `기기 연결` creates an explicit fresh cloud workspace/data-target attach preview; merging into or replacing an existing cloud generation is unavailable in the first release.

Crash recovery must never replay old outbound GitHub/iCloud jobs. Any old worker callback fails epoch/pointer validation, including a callback received after restart. Before-switch failure leaves the old active root untouched; restart that root only if it was previously running and validation succeeds, then reopen admission (cloud publication remains subject to current account/epoch checks). If recovery is uncertain, retain the fence and report `RESTORE_RECOVERY_REQUIRED`, never serve a mixed root. After-switch failure defaults to finishing startup of the new root with publication paused. Automatic rollback to the old pointer is allowed only while admission has continuously remained closed and the durable journal proves zero writes were accepted against the new root. Once admission has reopened, or that fact cannot be proved after a crash, never automatically roll back: preserve both roots, keep the new root authoritative and require recovery without discarding its accepted writes. Mark journal completion before reopening admission. Test every journal boundary and hashes, plus an admitted multipart mutation completing during drain: old preview rejects, completed write survives in old root, and no pointer/cloud publication occurs.

## Separate CloudKit record engine

Use a custom zone per dataset/generation in the private database. Every envelope carries contract version, generation, entity kind/UUID, logical operation UUID, immutable content digest and provenance. Preserve CKRecord system fields/change tags locally. A saved record's `lastOperationId` and content hash provide readback after a lost reply. CKSyncEngine serialized state is a cache; it is not the sole durable outbox or application commit log.

Tables planned (next free migration number at execution; current observed latest is 10): `cloud_bindings`, `cloud_jobs`, `cloud_outbox`, `cloud_inbox`, `cloud_records`, `cloud_tombstones`, `cloud_conflicts`, `cloud_version_ids`, `cloud_key_aliases`, `cloud_restore_state`, `cloud_history_events`. Common composite scope is binding/dataset/generation plus account/restore epochs. Outbox rows carry entity ID, operation ID, base server tag + base content, exact payload/hash, dependency IDs, origin device, state and retry metadata. Cloud records store server tag/base snapshot; inbox holds verified remote batches until dependencies/assets are available. No remote payload executes instructions.

Local mutation and outbox insertion occur in the **same SQLite transaction**, including deletion/cascade and resource writes. Generalize the existing issue hook carefully without overwriting history/GitHub hooks; other entity writes need explicit instrumentation. Failure to enqueue rolls back domain changes. Remote application runs one validated local transaction with `origin=cloud` and increments local revisions; it must not enqueue iCloud echoes or call GitHub publication hooks. Incoming protected transitions follow the explicit authority boundary below; remote actor strings, claimed receipts and CloudKit access never authorize local agent calls or owner-only import.

Freeze immutable assets by checksum and UUID storage key; validate bytes before exposing dependent content. Native transport uses CKAsset, with 20 MiB existing file cap; allow at most two asset staging operations. Missing data stays `waiting_assets`, never a successful dangling attachment. Commit attachments and references only when all dependencies exist. No claim of a CloudKit atomic transaction spanning asset bytes and an arbitrary workspace graph.

### Protected operations and authority provenance

The first record release has **no independently verified source-owner receipt protocol**. Same-account CloudKit access, a CKRecord change tag, a registered installation ID, `authorId`, `role:owner`, an audit row or a signed-looking blob proves neither that a specific source operation passed owner authorization nor that its approval remains applicable. An admitted peer is trusted only to deliver untrusted content proposals within the selected account/dataset, subject to schema/invariant checks; it receives no local owner grant. Never invoke `applyRemoteBatch` with a fabricated owner actor.

Wire `Provenance` is explicitly `unverified_remote`: source installation identifier and claimed actor/action are historical labels, plus optional bounded claimed-receipt evidence (type/digest, not credentials or keys). The importer supplies and verifies the actual binding/generation/epoch envelope independently of these claims. No wire discriminant such as `verified_owner` or `local_approved` may mint authority. The transport can acknowledge durable receipt of a proposal while product status remains `review_pending`; that is not application of its protected state.

Classify a protected operation using the same centralized owner-required predicates as the local domain, including issue close or modifications to closed issues, release approval, guidance designation/modification, owner-only project lifecycle and their destructive cascades. Unknown operation kinds or unclassifiable compound operations fail closed into inert proposals. Protected portions and all dependent effects remain unapplied; preserve the receiver's last locally authorized content and the exact remote alternative/digest as read-only proposal/history. Unrelated ordinary content can apply through an explicitly allowlisted import capability after normal invariant checks. That capability has no owner fallback, workflow/session response, release approval, agent grant, shell launch or GitHub publication authority.

The positive path in this release is **current local owner approval of concrete content**, not validation of an alleged remote owner. Present the content diff/target in the normal review surface (`확인이 필요한 변경`), with no technical trust/sync-strategy choice. `approveProtectedProposal(actor, proposalId, proposalRevision, expectedLocalRevision, operationId)` reauthenticates the actual local owner via the existing owner HTTP/MCP path, verifies current scope/both epochs, exact proposal digest and target revisions inside the domain transaction, then invokes the ordinary protected domain action with its existing confirmation rules. Server code may mint a transaction-local authorization context only after these checks; it binds the owner actor, action, entity/content digest, operation ID, account/dataset/generation, both epochs and revisions. It is neither serialized nor transferable, persisted as a credential, nor accepted from transport. An agent cannot mint it. Record the local approval as audit content and deduplicate exact operation replay; changed content, stale revision, changed epoch or revoked/expired owner session requires fresh authorization. Approval never resumes external jobs or grants a peer future authority. Each receiving device independently retains protected changes pending review; automatic protected-state convergence is explicitly unsupported.

Bootstrap uses the same rule: download into a separate read-only staged root; owner data-target confirmation must bind the exact staged content digest, protected-state summary and current boundary before activation. It does not authorize future protected changes. A conflict editor or snapshot import cannot bypass the protected-action gate. Pending proposals do not force a setup wizard or block unrelated ordinary edits; retain both versions indefinitely unless an authorized user explicitly discards content.

No device signing keys, peer enrollment, receipt verifier or new persistent credential is introduced by this plan. A later automatic protected-transition feature would require a separately reviewed protocol and explicit approval for persistent credential creation/storage: exact per-device key generation/storage and proof of possession; owner-authorized enrollment anchored outside untrusted CloudKit metadata; independently authenticated peer/key fingerprints and allowed actions; receipts bound to canonical content/action/entity/operation/dataset/generation/account epoch and nonce; durable replay protection; authenticated revocation with freshness checks before use, rotation and account/restore reset semantics; unknown, offline-stale or revoked trust failing closed. CloudKit record existence cannot be its own trust root. Those are prerequisites for a future design, not setup steps authorized or required for Stage A–D here.

Required authority fixtures: a real local owner action emits only a remote proposal, then explicit authenticated local approval applies exactly once; an agent source, forged/edited actor metadata, fake signed-looking receipt, duplicate/replayed receipt, receipt claiming a revoked device, and account/generation/restore-epoch-cross receipt all remain inert. Even an apparently well-formed receipt is unsupported in this release. Test receipt replay before and after local approval: no second protected action/audit revision or outbound side effect. Ordinary safe-field import still succeeds. Approval by an expired session, scoped agent or mismatched content/revision/epoch fails while both versions remain preserved.

### Exact merge default

For each mutable scalar/whole text/whole labels array, compare canonical values in base B, local L and remote R: if L=B use R; if R=B use L; if L=R use that value; otherwise retain B/L/R in a durable conflict and keep the last accepted server projection visible for ordinary fields; protected fields retain the receiver's last locally authorized projection until the approval rule above succeeds. Preserve the local alternative in a visible `별도 변경이 보관됨` recovery item; do not silently discard it. No wall-clock last-write-wins or automatic Markdown line merging. Unrelated entities continue syncing. Conflict save is a normal content edit against current server tag plus conflict revision; default is preserve both indefinitely, with no strategy question. Owner can edit the retained text into the normal editor; explicit discard is destructive consent. Conflict records and preserved alternatives themselves must be durable and delivered before acknowledging the divergent outbox item.

Allocator/graph caps for the first record prototype: 100 mutations per batch, 1,000 active structural edges per project, 256 KiB serialized graph head. The first-sync bootstrap from an existing local workspace seeds IDs and claims under a fresh generation before enabling edits from another device. Existing cloud workspace is downloaded into a distinct local data root, with current local root preserved. Automatic merge of unrelated existing workspaces is out of scope. No technical decision is exposed to the user as a solution to collision handling.

### Deletion, retries and generation boundaries

Delete writes an immutable tombstone (entity UUID/kind, generation, operation UUID, accepted server tag and cascade boundary) in the same local transaction as domain deletion. Parent deletion includes the known dependent set and a parent tombstone fence: late child creation referencing a deleted parent stays preserved conflict, never recreates parent. Delete-versus-edit keeps tombstone active and alternate content in recovery; no automatic resurrection. Soft-deleted resources follow the same contract.

No tombstone garbage collection in the first record release. A future compaction requires a new generation and explicit stale-client rebootstrap. Expired change tokens cause a full remote inventory/tombstone reconciliation while preserving unsent local work. Missing records are not deletion evidence. Missing/deleted zones or generation mismatch pause with `CLOUD_DATASET_MISSING`/`GENERATION_CHANGED`; never auto-create a zone from an old local copy. Restore never rotates another device's active cloud generation.

Retry only known retriable failures; bounded exponential backoff with provider retry-after, one scheduler per binding and persisted next-attempt. Quota stops automatic upload attempts until explicit retry or provider state change; disk-full does not delete previous backup. Partial batch success acknowledges exact successful IDs, conflicts remain queued/recorded and unknown results require readback. Server tags, not clocks, are concurrency authority. All callbacks check binding, both epochs and active root before any local write.
