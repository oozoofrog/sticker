# 이슈 변경 이력과 선택 복원

이슈의 제목, 본문, 상태, 우선순위, 담당자, 라벨, 목표·발견·수정 버전만 변경 전후 값으로 기록합니다. HTTP와 MCP 수정은 같은 검증·기록 경로를 사용합니다. 라벨은 기존 이슈 저장 규칙처럼 공백 제거와 중복 제거 후 입력 순서를 유지합니다. 인증 헤더, 토큰, 임의 요청 객체는 이력에 복사하지 않습니다.

활동과 변경 이력은 이슈 수정 트랜잭션 안에서 함께 저장됩니다. 버전 삭제의 참조 해제, 출시 이월, 템플릿 생성도 기록됩니다. 실패한 이월 항목·중복 생성·복원 재시도는 이력을 중복 생성하지 않습니다. 관계·자료 연결처럼 revision만 바뀌는 기록은 복원 가능한 필드 변경과 구분됩니다. 생성에는 존재하지 않는 이전 값을 만들지 않으며, 기존 활동의 누락된 과거 값도 현재값으로 채우지 않습니다.

## HTTP

- `GET /api/issues/:id/history`: 현재 프로젝트 권한으로 활동과 비교 가능 여부 조회.
- `GET /api/issues/:id/history/:changeId`: 허용 필드별 기록된 이전·이후 값.
- `POST /api/issues/:id/restore/preview`: 소유자 전용. `{changeId, side: 'before'|'after', fields, revision}`.
- `POST /api/issues/:id/restore`: 같은 선택에 UUID `operationId`를 추가합니다.

복원 값은 클라이언트가 보내지 않습니다. 서버가 해당 이슈의 이력에서 읽고 현재 revision·권한·버전 참조를 다시 확인합니다. 고르지 않은 필드는 변경하지 않습니다. 삭제되었거나 다른 프로젝트에 속한 버전은 복원하지 않습니다. 복원도 새 revision·주체·시각·원본 변경 ID를 갖는 새 이력입니다. 에이전트는 수정 권한이 있어도 복원할 수 없습니다.

동일 주체·작업 UUID·선택의 재시도는 이미 적용된 복원 이력과 현재 이슈를 반환합니다. 같은 UUID를 다른 선택에 재사용하면 충돌합니다. 응답이 끊겼을 때 화면의 결과 재확인은 같은 UUID를 사용합니다. 최신 수정과 충돌하면 선택을 유지하지만 최신 현재값을 다시 검토하고 확정해야 합니다.

## MCP와 화면

읽기 전용 `sticker_list_issue_history`, `sticker_get_issue_change`가 같은 현재 범위 검사를 사용합니다. 에이전트 복원 도구는 없습니다. 변경 기록의 비교 버튼에서 변경 필드만 확인하고, 소유자는 이전/이후 시점과 필드를 골라 현재값→복원값을 확인합니다. 본문은 실행되지 않는 텍스트이며 외부 이미지도 불러오지 않습니다.

선택 취소와 확인 전 뒤로가기에는 변경 작업이 발생하지 않습니다. 복원 요청 중 중복 전송·이동을 막고, 응답을 잃은 요청은 같은 작업으로 확인합니다. 좁은 화면에서는 전후 값을 세로로 표시합니다.

## 저장과 백업

스키마9는 기존 이슈·댓글·첨부를 유지하며 새 `issue_changes`, `issue_field_changes`, `issue_restore_operations`를 추가합니다. 이력의 수명은 해당 이슈를 따릅니다. 삭제한 이슈·파일·데이터베이스 전체 복구 기능이 아닙니다. 지원되는 이전 백업은 읽기 전용 검증 후 시작 시 순서대로 마이그레이션합니다. 이력 JSON, revision/활동/원본 연결, 복원 작업 기록도 백업에서 검증합니다.
