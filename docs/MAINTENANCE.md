# 유지보수와 업데이트 경계

스티커는 UI와 MCP가 같은 HTTP API를 사용하는 모듈형 단일 서버입니다. SQLite와 첨부 파일의 소유자는 서버 하나이며, 여러 STDIO MCP 어댑터는 DB 파일을 직접 열거나 데이터 볼륨을 공유하지 않습니다.

## 지원하는 상태와 제어

- `/healthz`: 기존 프로세스 생존 확인. 유지보수 중에도200입니다.
- `/readyz`: 요청 수락 가능하면200, 유지보수/종료 중503입니다. 캐시하지 않습니다.
- `GET /api/maintenance`: 인증된 사용자가 `contractVersion:1`, `instanceId`, `revision`, `state`, `startedAt`, `drained`를 읽습니다. 개별 작업자 정보나 비밀은 포함하지 않습니다.
- 기존 소유자만 `POST /api/maintenance/begin` 또는 `/resume`를 호출할 수 있습니다. 요청은 방금 읽은 `instanceId`, `revision`, `confirm:true`를 사용합니다. 기존 인증·Origin 검증이 그대로 적용됩니다.
- 서버가 바뀌었거나 revision이 오래됐으면409입니다. 현재 상태에서 같은 동작은 추가 전환을 만들지 않습니다. 종료 중인 인스턴스는 다시 시작 상태로 바꿀 수 없습니다.

`begin`은 새 **업무 API 읽기와 쓰기 모두**를503 `MAINTENANCE`로 거절합니다. 상태/세션/접근 방식의 정확한 지원 경로만 유지합니다. `drained:true`는 이미 수락한 요청과 추적하는 비동기 작업이 끝났다는 뜻이지, 에이전트 전체가 멈추거나 메시지를 읽었다는 뜻이 아닙니다. 기존 업로드 파서와 GitHub 외부 확인은 클라이언트가 연결을 끊어도 실제 콜백/Promise 완료까지 추적합니다.

## MCP와 UI의 회복

점검 중 호출은 기존 오류 형식과 함께 `retryAfterSeconds:5`, 유지보수 스냅샷을 받습니다. 이는 최소 재확인 간격 안내이며5초 뒤 복구 약속이 아닙니다. UI는 다음 요청의 점검 오류를 표시하며, MCP STDIO는 같은 서버의 begin/resume 동안 살아 있고 사용자가 명시적으로 다시 호출할 수 있습니다. **자동 쓰기 재전송은 없습니다.**

전체 작업자에게 push/broadcast하거나 읽음·중단을 확인하는 기능은 없습니다. 새 API 호출을 하지 않는 클라이언트는 알림을 못 받을 수 있습니다. 도구 반환 내용은 새 실행 권한이 아닙니다.

## 안전한 짧은 업데이트 순서

1. 실행 중 서비스를 바꾸기 전에 새 이미지와 계약을 검증합니다.
2. 기존 소유자 인증으로 현재 유지보수 상태를 읽고 begin합니다. 필요한 작업자 연락은 실제로 사용 가능한 채널에서 별도로 수행합니다.
3. `drained:true`를 확인합니다. 끝나지 않는 작업을 완료했다고 표시하지 않습니다. 자동 재시작이나 전체 Codex 종료를 하지 않습니다.
4. 먼저 `docker compose stop -t 30 sticker`로 대상 서버를 명시적으로 중지합니다. 그 다음 `scripts/backup.sh`를 실행하면 이미 중지된 상태를 유지한 채 SQLite+uploads를 함께 백업합니다. 업데이트 전에 다시 쓰기를 받아들이는 틈을 만들지 않습니다. 단독 백업 스크립트는 원래 실행 중인 서비스를 자동 재시작하는 기존 의미를 유지하므로, 계획된 업데이트에서는 이 선행 중지 단계를 생략하지 마세요.
5. 검증된 이미지로 교체하고 시작한 뒤 readiness, 데이터·파일 보존, 실제 대표 MCP 호출을 검증합니다. 처음부터 백업과 교체 사이에 사용자가 쓰기를 재개할 수 있는 자동 무중단 절차라고 표시하지 않습니다.

SIGTERM/SIGINT는 새 요청 수락을 중단하고 진행 중 작업과 HTTP close를 기다린 뒤 DB를 닫습니다. 기존10초 예산을 초과하거나 close가 실패하면 exit1로 종료하며 완료로 보고하지 않습니다. 동작 중인 Promise가 있는데 DB를 먼저 명시적으로 닫지는 않습니다. 컨테이너 강제 종료의 crash recovery가 정상 drain과 같은 것은 아닙니다.

## 아직 지원하지 않는 보장

- 무중단 업데이트·자동 전체 작업자 일시정지/재개
- 서버 컨테이너 재생성 후 이전 `network_mode: service:sticker` STDIO의 투명한 재연결
- 온라인 DB+첨부 백업 및 임의 구버전으로 안전한 자동 롤백
- 분리된 UI/MCP 패키지의 모든 버전 조합 호환

현재 백업은 일관된 오프라인 방식입니다. SQLite snapshot만으로 파일 수명/삭제/업로드 경합을 해결할 수 없습니다. 롤백은 코드와 스키마 호환을 먼저 확인하고, 복원 시 백업 이후 쓰기를 버리지 않도록 별도 판단해야 합니다. 자격증명 설정은 데이터 백업과 별도로 보존합니다.
